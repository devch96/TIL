# 느려진 서비스, 어디부터 봐야 할까

------

## 처리량과 응답 시간

- 성능이 저하되면 가장 눈에 띄는 현상은 결과가 늦게 표시되는 것
  - 너무 오래 걸려 타임아웃 에러가 발생하기도 함
- 사용자는 동작하기 까지 걸린 시간을 성능으로 판단하지만 다양한 지표가 성능과 관련되어 있음
  - 네트워크 속도, 디스크 속도, 메모리 크기, 디바이스의 CPU 속도 등
- 응답 시간과 처리량은 서버 성능과 관련 있는 중요한 지표

### 응답 시간

- 사용자의 요청을 처리하는 데 걸리는 시간을 의미
  - API를 호출하고 JSON 응답을 받을 때까지 소요된 시간
- 클라이언트(앱 or 브라우저)가 서버로 요청을 보내는 과정은 크게 2단계
  - 서버에 연결: TCP를 이용해 서버에 연결
  - 데이터 전송: 프로토콜에 따라 데이터를 서버에 전송
- 서버는 로직을 실행한 다음 응답 데이터를 클라이언트에 전송
- 응답 시간은 2가지로 나누어 측정하기도 함
  - TTFB(Time to First Byte): 응답 데이터 중 첫 번째 바이트가 도착할 때까지 걸린 시간
  - TTLB(Time to Last Byte): 응답 데이터의 마지막 바이트가 도착할 때까지 걸린 시간
- 서버 성능을 올바르게 평가하라면 데이터 특성이나 네트워크 환경을 고려해 TTFB와 TTLB 중 적절한 지표를 선택해 측정해야 함
  - 데이터의 크기가 작다면 TTFB와 TTLB의 차이가 크지 않음
  - 파일 다운로드처럼 데이터의 크기가 크다면 TTFB와 TTLB의 차이가 큼
- 응답 시간은 1초보다 짧을 때가 많기 때문에 응답 시간을 잴 때는 1/1000 초인 밀리초 단위를 사용함
  - 10ms
- 응답 시간은 API 요청 전송 시간, 서버의 처리 시간, API 응답 전송 시간으로 나뉨
- 서버 개발자는 주로 서버의 처리 시간을 확인함
- 서버 처리 시간은 다음과 같은 요소를 포함함
  - 로직 수행 (if, for 등)
  - DB 연동 (SQL 실행)
  - 외부 API 연동
  - 응답 데이터 생성(전송)
- DB 연동과 외부 API 연동이 큰 비중을 차지함
  - 응답 시간을 줄일 때 DB 연동과 API 연동 시간에 집중해야 함

### 처리량

- 단위 시간당 시스템이 처리하는 작업량을 의미하는데 흔히 TPS나 RPS로 처리량을 나타냄
- TPS는 초당 트랜잭션 수: Transaction For Second의 약자
- RPS는 초당 요청 수: Request Per Second의 약자
- 최대 TPS를 초과하는 요청이 들어왔을 때 사용자 입장에서는 응답 시간이 증가하는 문제를 보여줌
- 다음 2가지 방법을 고려해야 함
  - 서버가 동시에 처리할 수 있는 요청 수를 늘려 대기 시간 줄이기
  - 처리 시간 자체를 줄여 대기 시간 줄이기
- 성능을 개선하려면 먼저 현재 서버의 TPS와 응답 시간을 알아야 함
- 막연히 성능이 느리다고 이것저것 시도하면 안됨

## 서버 성능 개선 기초

### 병목 지점

- 성능 문제는 사용자가 늘면서 점차 나타남
  - 트래픽이 늘고 데이터가 쌓이면서 간헐적으로 응답시간이 느려지는 현상이 발생
- 성능 문제가 터지는 전형적인 증상
  - 순간적으로 모든 사용자 요청에 대한 응답 시간이 심각하게 느려진다. 
  10초 이상 걸리는 요청이 늘어나고 다수의 요청에서 연결 시간 초과와 같은 오류가 발생한다
  - 서버를 재시작하면 잠시 괜찮다가 다시 응답 시간이 느려지는 현상이 반복된다
  - 트래픽이 줄어들 때까지 심각한 상황이 계속된다
- 트래픽이 증가하면서 성능 문제가 발생하는 주된 이유는 시스템이 수용할 수 있는 최대 TPS를 초과하는 트래픽이 유입되기 때문
- TPS를 높이려면 성능 문제가 발생하는 지점을 찾아야 함
  - 경험에 의해 감으로 오래 걸릴 것 같은 코드를 추측할 수도 있지만 가능하다면 실제 실행 시간을 측정해야 함

### 수직 확장과 수평 확장

- 성능 문제를 일으키는 원인을 찾았다면 빠르게 적용할 수 있는 개선안을 도출해야 함
- 수직 확장(scale-up)은 CPU, 메모리, 디스크 등의 자원을 증가시키는 것을 말함
  - 클라우드 환경에서 비교적 빠르게 시도할 수 있는 방법
- 수직 확장은 즉각적인 효과를 바로 얻을 수 있지만 트래픽이 지속해서 증가하면 언젠가 결국 또다시 성능 문제가 발생함
  - 수직 확장을 반복할 수는 없음
  - 비용이 많이 들고 한 대의 장비가 감당할 수 있는 용량에도 한계가 있음
- 트래픽이 증가하면 서버를 추가로 투입해 TPS를 높이는 방법도 고려해야 하는데 이것이 수평 확장 (scale-out)

### DB 커넥션 풀

- DB를 사용하려면 다음과 같이 3단계를 거친다
  - DB에 연결한다
  - 쿼리를 실행한다
  - 사용이 끝나면 연결을 종료한다
- 서버와 DB는 네트워크 통신을 통해 연결하는데 네트워크 연결을 생성하고 종료하는 데 긴 시간이 걸린다
- DB 커넥션 풀은 DB에 연결된 커넥션을 미리 생성해서 보관함
- 애플리케이션은 DB 작업이 필요할 때 풀에서 커넥션을 가져와 사용하고 작업이 끝나면 다시 풀에 반환
- 커넥션 풀은 다양한 설정을 제공하며 중요한 설정은 다음과 같다
  - 커넥션 풀의 크기(최소, 최대)
  - 풀에 커넥션이 없을 때 커넥션을 구할 때까지 대기할 시간
  - 커넥션의 유지 시간(최대 유휴 시간, 최대 유지 시간)

### 커넥션 풀 크기

- 커넥션 풀에 미리 생성해둘 커넥션 개수를 지정하는 설정
- 서버는 주로 DB와 통신하기 때문에 DB 연결을 관리하는 DB 커넥션 풀 크기를 잘못 설정하면 성능에 큰 영향을 줌
- 풀에서 커넥션을 얻기 위해 대기하는 시간을 줄이려면 전체 응답 시간과 TPS를 고려하여 커넥션 풀 크기를 지정해야 함
  - 커넥션 풀 크기가 5이고 한 요청에서 쿼리를 실행하는 데 0.1초가 걸린다고 가정
  - 1초에 처리할 수 있는 요청 수는 50
  - 즉 동시에 50개의 요청이 들어오더라도 1초 안에 처리가 끝남
  - 반면 커넥션 풀 크기가 5초이고 한 요청의 쿼리 실행 시간이 0.5초라면 1초에 처리할 수 있는 요청의 수는 10으로 줄어듬
  - 50개의 요청이 들어오면 5초가 걸림
    - 어떤 요청은 0.5초만에 실행이 끝나지만 다른 요청 커넥션을 구하기 위해 4.5초를 대기할 수도 있음
- 커넥션 풀의 구현 방식에 따라 다르지만 일반적인 커넥션 풀은 최소 크기와 최대 크기를 설정할 수 있음
  - 최소 크기를 10, 최대 크기를 20으로 지정하면 동시에 들어오는 요청이 10개 이하라면 10, 10개를 초과하면 커넥션 수를 늘려
  요청을 처리하고 최대 20까지 늘림
- 일반적으로 트래픽은 증가했다가 감소하는 패턴이 있기 때문에 커넥션 풀 크기도 트래픽이 적은 시간대는 최소 크기로 유지하고 트래픽이 높은
시간대에는 최대 크기로 확장해서 유지할 수 있음
- 커넥션 풀 크기를 무턱대고 늘리면 안됨
  - DB 상태를 보고 늘려야 함
- DB 서버의 CPU 사용률이 80%에 육박하는 상황에서 커넥션 풀 크기를 늘리면 DB에 가해지는 부하가 더 커져 쿼리 실행 시간이 급격히 증가할 수 있음
  - 이러한 상황에서는 커넥션 풀의 크기를 오히려 줄여서 DB 서버가 포화 상태에 이르지 않도록 해야 함

### 커넥션 대기 시간

- 대기 시간이란 풀에 사용할 수 있는 커넥션이 없을 때 커넥션을 얻기 위해 기다릴 수 있는 최대 시간을 의미
- 대기 시간 안에 커넥션을 구하지 못하면 DB 연결 실패 에러가 뜸
- 응답 시간이 중요한 서비스는 커넥션 대기 시간을 가능한 한 짧게 설정해야 함
  - 보통의 경우라면 0.5~3초 사이
- 대기 시간을 짧게 설정하면 커넥션 풀이 모두 사용 중일 때 빠르게 일시적 오류 와 같은 에러 응답을 사용자에게 보여줄 수 있음
- 에러를 응답하는 게 부정적으로 보일 수 있으나 대기 시간 때문에 긴 시간 동안 무응답으로 유지되는 것보다 빠르게 에러를 반환하는 것이 더 남
- 커넥션을 얻지 못했을 때 빠르게 에러를 응답해야 서버의 부하가 증가하는 것도 방지할 수 있음
  - 풀에서 커넥션을 구하지 못한 요청은 대기중이며 그 중 클라이언트의 일부가 요청을 취소하더라도 서버는 일정 시간 동안 하던 작업을 즉시 중단하지 않기 때문에
  대기 중인 요청 수는 증가함
  - 요청 수가 증가하면 서버에 가해지는 부하도 커지게 됨

### 최대 유휴 시간, 유효성 검사, 최대 유지 시간

- 요청이 없는 시간대에는 풀에 있는 커넥션도 사용되지 않음
  - 커넥션이 사용되지 않는 시간이 길어지면 연결이 끊길 수 있음
- 풀에 있는 커넥션이 일정 시간 이상 사용되지 않으면 DB와의 연결이 끊어질 수 있음
- 연결 끊김으로 인해 발생하는 에러르 방지하기 위해 2가지 기능을 제공함
  - 최대 유휴 시간 지정
  - 유효성 검사 지원
- 최대 유휴 시간은 사용되지 않는 커넥션을 풀에 유지할 수 있는 최대 시간을 의미
- 최대 유휴 시간을 30분으로 설정하면 30분 이상 사용되지 않은 커넥션은 종료되어 풀에서 제거됨
  - DB에 설정된 비활성화 유지 시간보다 짧게 설정하면 DB가 연결을 끊기 전에 풀에서 커넥션을 제거할 수 있음
- 유효성 검사는 커넥션이 정상적으로 사용할 수 있는 상태인지 여부를 확인하는 절차
- 커넥션 풀의 구현 방식에 따라 커넥션을 풀에서 가져올 때 유효성을 검사하거나 주기적으로 검사함
  - 유효하지 않은 커넥션은 풀에서 제거함

### 서버 캐시

- DB 서버를 확장하지 않고도 응답 시간과 처리량을 개선하고 싶다면 캐시 사용을 고려할 수 있음
- 캐시는 일종의 키, 값 쌍을 저장하는 데이터 저장소
- 캐시에 데이터를 저장해두면 동일한 데이터를 요청할 때 DB가 아닌 캐시에서 데이터를 읽어와 응답할 수 있음

### 적중률과 삭제 규칙

- 캐시가 얼마나 효율적으로 사용되는지는 적중률(hit rate)로 판단할 수 있음
  - 캐시에 존재한 건수/캐시에서 조회를 시도한 건수
- 적중률이 높을수록 DB와의 연동이 줄어들고 응답 시간 감소, 처리량 증가, DB 부하 감소로 이어짐
- 적중률을 높이는 가장 간단한 방법은 캐시에 최대한 많은 데이터를 저장하는 것
- 하지만 모든 데이터를 저장할 수 없으니 캐시가 가득 차 있는 상태에서 새로운 데이터를 캐시에 저장하면 기존에 있던 데이터 중 하나를 제거해야 함
- 삭제할 대상을 선택할때는 다음과 같은 규칙을 사용
  - LRU(Least Recently Used): 가장 오래전에 사용된 데이터를 제거
  - LFU(Least Frequently Used): 가장 적게 사용된 데이터를 제거
  - FIFO(First In First Out): 먼저 추가된 데이터를 먼저 삭제
- 오래된 데이터는 덜 조회되므로 오래된 데이터는 미리 삭제하는 것이 좋음
- 캐시에는 유효 시간(만료 시간)을 설정하는 방식도 함께 사용됨

### 로컬 캐시와 리모트 캐시

- 로컬 캐시는 서버 프로세스와 동일한 메모리를 캐시 저장소로 사용
- 리모트 캐시는 별도 프로세스를 캐시 저장소로 사용
- 로컬 캐시 구현 기술로는 Caffeine(자바), go-cache(Go), node-cache(Node.js) 등이 있음
- 로컬 캐시는 서버 프로세스와 캐시가 동일한 메모리 공간을 사용하므로 캐시 데이터에 빠르게 접근할 수 있고 외부 연동이 필요하지 않아
구조를 단순하게 유지할 수 있다는 장점이 있다
- 단점은 캐시에 저장할 수 있는 데이터 크기에 제한이 있고 서버 프로세스를 재시작하면 메모리에 존재하던 캐시 데이터가 모두 삭제되어 일시적으로 캐시 효율(적중률)이
순간적으로 떨어진다는 단점이 있음
- 리모트 캐시는 로컬 캐시와 정반대의 장단점을 가짐
- 캐시에 보관할 데이터 규모가 작고 변경 빈도가 매우 낮다면 로컬 캐시로 충분함
- 배포 빈도가 높은 서비스라면 리모트 캐시 사용을 적극적으로 고려해야 함

### 캐시 사전 적재

- 트래픽이 순간적으로 급증하는 패턴을 보인다면 캐시에 데이터를 미리 저장하는 것도 고려할 필요가 있음

### 캐시 무효화

- 유효하지 않은 데이터를 적절한 시점에 캐시에서 삭제하는 것을 반드시 신경 써야 함
- 캐시에 보관된 데이터의 원본이 바뀌면 캐시에 보관된 데이터도 함께 변경하거나 삭제해야 함
- 가격 정보, 게시글 내용처럼 민감한 데이터는 변경되는 즉시 캐시를 무효화해야 함
- 변경에 민감한 데이터는 로컬 캐시가 아닌 리모트 캐시에 보관해야 함
  - 로컬 캐시는 자신의 데이터만 변경하지 다른 서버의 로컬 캐시는 변경하지 않기 때문
- 최근 인기 글 목록을 캐시에 저장한 경우 최근 인기 글 목록이 바뀌고 몇 분 뒤에 캐시 데이터가 변경되더라도 서비스에 심각한 문제는
일어나지 않기 때문에 캐시의 유효 시간을 설정하여 주기적으로 갱신하는 방식을 사용해도 됨

### 가비지 컬렉터와 메모리 사용

- 가비지 컬렉터는 개발자가 메모리를 직접 관리해야 하는 부담을 줄여줌
- 코드로 메모리를 관리할 수 없기 때문에 보안 이슈를 줄여주는 장점도 있음
- 하지만 가비지 컬렉터는 응답 시간에 영향을 줄 수 있음
- 자바에서는 가비지 컬렉터가 실행되는 동안 애플리케이션의 실행이 일시 중단되는데 이것을 Stop The World라고 표현함
- JVM에 할당 된 최대 힙 크기를 줄이면 GC가 탐지하고 제거해야 할 미사용 객체의 개수와 크기가 줄어듬
- 하지만 실제 애플리케이션이 필요한 만큼은 있어야 하므로 메모리 사용 패턴에 맞게 최대 힙 크기를 조정해야 함
- 한 번에 대량으로 객체를 생성하는 것도 주의해야 함
- 파일 다운로드와 같은 기능을 구현할 때는 스트림을 활용해야 함

```java
byte[] bytes = Files.readAllBytes(Path.of("path"));
// 파일을 한 번에 메모리에 로딩하면 30MB 크기의 파일을 100명이 동시에 다운로드 하면 3GB의 메모리가 필요
InputStream is = Files.newINputstream(Path.of("path"));
byte[] buffer = new Byte[8192]; // 8kb 메모리
// 파일을 한 번에 읽지 않고 8KB씩 끊어서 읽으면 100명이 동시에 다운로드해도 필요한 메모리는 800KB
```

### 응답 데이터 압축

- 응답 시간에는 데이터 전송 시간이 포함되는데 전송 시간은 2가지 요인에 영향을 받음
  - 네트워크 속도
  - 전송 데이터 크기
- 서버는 사용자의 네트워크 속도를 제어할 수 없지만 전송하는 데이터의 크기는 제어할 수 있음
- 응답 데이터를 압축해서 전송하면 데이터 전송량을 크게 줄일 수 있음
- 응답 데이터를 압축할 때는 다음 사항을 고려
  - html, css, js, json과 같은 텍스트 형식의 응답은 압축률이 높아 효과적이지만 이미지는 이미 압축한 데이터이기에 효과가 없음
  - 웹 서버에서 압축을 적용했더라도 방화벽이 이를 해제해 응답할 수 있기에 방화벽 설정도 확인해야 함

### 정적 자원과 브라우저 캐시

- HTTP 프로토콜에서는 데이터를 응답할 때 Cache-Control 이나 Expires 헤더를 통해 클라이언트가 응답 데이터를 일정 시간 동안 저장해둘 수 있도록
설정할 수 있음
- 브라우저 캐시를 활용하면 서버 입장에서도 전송해야 할 트래픽이 줄어들어 네트워크 전송 비용을 아낄 수 있음

### 정적 자원과 CDN

- 브라우저 캐시는 브라우저 단위로 동작하기 때문에 동시에 많은 사용자가 접속하면 순간적으로 많은 양의 이미지, js, css를 전송하게 됨
- 빠르게 네트워크가 포화되어 응답 시간이 급격히 느려짐
- CDN은 (Content Delivery Network), 컨텐츠 전송 네트워크로 콘텐츠를 제공하기 위한 별도의 네트워크를 의미함
- CDN은 여러 지역에 서버를 두고 사용자는 가까운 곳에 위치한 서버에 연결해서 콘텐츠를 다운로드 함

### 대기 처리

- 순간적으로 폭증하는 트래픽을 처리하기 위해 서버와 DB를 증설하는 것이 잘못된 방법은 아니나 비용의 문제가 있음
  - 짧은 시간을 버티기 위해서 투입해야 하는 비용이 크기 때문
- 수용할 수 있는 수준의 트래픽만 받아들이고 나머지는 대기 처리하는 것이 남
