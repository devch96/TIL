# 비동기 연동, 언제 어떻게 써야 할까

## 동기 연동과 비동기 연동

- 동기 방식은 순차적으로 실행
- 코드의 순서가 곧 실행 순서
- 동기 방식은 프로그램의 흐름을 직관적으로 이해할 수 있고 디버깅도 용이
- 동기 방식이 외부 연동을 만나면 고려해야 함
  - 포인트 지급 서비스 연동에 실패하면 로그인도 실패해야 할까?
  - 포인트 지급 서비스에 장애가 전파되는 현상
  - 포인트 지급에 실패하더라도 로그인 자체는 정상적으로 동작해야 하고 나머지 기능을 사용할 수 있기를 원함
  - 연동 외부 서비스의 응답 시간도 고려
- 다음 작업을 진행하기 위해 반드시 외부 연동 결과가 필요한 게 아니라면 동기 방식 대신 비동기 방식으로 연동하는 것을 고민해 볼 필요가 있음
- 비동기 방식은 한 작업이 끝날 때까지 기다리지 않고 바로 다음 작업을 처리함
- 비동기 방식을 사용하면 외부 연동이 끝날때까지 기다리지 않고 다음 작업을 진행할 수 있기 때문
- 비동기 방식으로 연동해도 크게 문제가 되지 않는 몇 가지 예
  - 쇼핑몰에서 주문이 들어오면 판매자에게 푸시 보내기(푸시 서비스 연동)
  - 학습을 완료하면 학생에게 포인트 지급(포인트 서비스 연동)
  - 컨텐츠를 등록할 때 검색 서비스에도 등록(검색 서비스 연동)
  - 인증 번호를 요청하면 SMS로 인증 메시지 발송(SMS 발송 서비스 연동)
- 비동기 방식으로 연동해도 되는 공통적인 특징
  - 연동에 약간의 시차가 생겨도 문제가 되지 않음
  - 일부 기능은 실패했을 때 재시도가 가능
  - 연동에 실패했을 때 나중에 수동으로 처리할 수 있는 기능이 있음
  - 연동에 실패했을 때 무시해도 되는 기능이 있음

## 별도 스레드로 실행하기

- 비동기 연동을 하는 가장 쉬운 방법

```java
public OrderReuslt placeOrder(OrderRequest req) {
    // 주문 생성 처리
    
    // 별도 스레드를 이용해서 푸시를 비동기로 발송
    new Thread(() -> pushClient.sendPush(pushData)).start();
    
    return successResult();
}

// 매번 스레드를 생성하는 대신 스레드 풀 사용
ExecutorService executor = Executors.newFixedThreadPool(50);

public OrderResult placeOrder(OrderRequest req) {
    // 주문 생성 처리
    
    // 스레드 풀을 이용해서 푸시를 비동기로 발송
    executor.submit(() -> pushClient.sendPush(pushData));
    
    return successResult();
}
```

- 프레임워크가 제공하는 비동기 기능을 사용하는 방법도 있음
  - 스프링의 경우 @Async 어노테이션을 이용한 비동기 실행 제공
  - 특정 메서드를 비동기로 실행할 수 있음
- @Async 어노테이션을 사용할 때는 메서드 이르멩 비동기 실행과 관련된 단어를 추가하는 것이 좋음
  - 코드를 읽는 사람은 메서드를 실행할 때 비동기로 실행된다는 걸 알아야함
  - 비동기로 실행된다는 사실을 모른 채 try-catch로 익셉션 처리 코드를 추가하다가 catch 못하는 경우가 생기면 안됨

```java
public Order placeOrder(OrderRequest req) {
    // 주문 생성 처리
    try {
        pushService.sendPush(pushData);
    } catch(Exception ex) {
        // sendPush()가 비도이로 실행되므로 catch 블록은 동작하지 않음
    }
}
```
- 별도 스레드로 실행되는 코드는 내부에서 연동 과정에서 발생한 오류를 직접 처리해야 함

```java
@Async
public void sendPushAsync(PushData pushData) {
    try {
        pushClient.sendPush(pushData);
    } catch(Exception e) {
        try {
            Thread.sleep(500);
        } catch(Exception ex) {}
        try {
            pushClient.sendPush(pushData); //재시도를 하거나
        } catch(Exception e1) {
            // 실패를 로그로 남기거나
        }
    }
}
```

## 메시징

- 서로 다른 시스템 간에 비동기로 연동할 때 주로 사용하는 방식은 메시징 시스템을 사용하는 것
- 메시징 시스템은 데이터 연동이 필요한 두 시스템 사이에 위치함
- 시스템 A는 전달할 데이터를 가진 메시지를 생성해서 메시징 시스템에 전송
- 메시징 시스템은 메시지를 다시 시스템 B에 전달하고 시스템 B는 전달받은 데이터를 이용해 작업을 처리
- 메시징 시스템을 사용하면 구조가 복잡해지는 대신 이점을 얻을 수 있음
  - 두 시스템이 서로 영향을 주지 않음
    - 시스템 A의 트래픽이 갑자기 증가하여도 시스템 B에 성능 저하가 발생하지 않음
    - 시스템 B의 성능이 저하되더라도 시스템 A는 영향을 받지 않음
  - 확장이 용이함
    - 시스템 A가 시스템 C에도 데이터를 전송해야 한다고 가정할때 메시징 시스템이 없이 직접 전송했다면 시스템 A에 새로운
    코드를 추가해야 하지만 메시징 시스템을 사용하면 시스템 C를 메시징 시스템에 연결하기만 하면 됨
- 메시징 시스템 용도로 많이 사용되는 기술은 카프카, 래빗MQ, 레디스 pub/sub 등이 있음

### 카프카 주요 특징

- 높은 처리량을 자랑. 초당 백 만 개 이상 메시지 처리 가능
- 수평 확장이 용이. 서버(브로커), 파티션, 소비자를 늘리면 됨
- 카프카는 메시지를 파일에 보관해서 메시지가 유실되지 않음
- 1개의 토픽이 여러 파티션을 가질 수 있는데 파티션 단위로 순서를 보장하지만 토픽 수준에서는 순서를 보장하지 않음
- 소비자는 메시지를 언제든지 재처리할 수 있음
- 풀(pull) 모델을 사용. 소비자가 카프카 브로커에서 메시지를 읽어 가는 방식

### 래빗MQ 주요 특징

- 클러스터를 통해 처리량을 높일 수 있음. 카프카보다는 더 많은 자원을 필요로 함
- 메모리에만 메시지를 보관하는 큐 설정을 사용하면 장애 상황 시 메시지가 유실될 수 있음
- 메시지는 큐에 등록된 순서대로 소비자에 전송됨
- 메시지가 소비자에 전달됐는지 확인하는 기능을 제공
- 푸쉬(push) 모델을 사용. 래빗MQ 브로커가 소비자에 메시지를 전송함.
소비자의 성능이 느려지면 큐에 과부하가 걸려 전반적으로 성능 저하가 발생할 수 있음
- AMQP, STOMP 등 여러 프로토콜을 지원하고 게시/구독 패턴뿐만 아니라 요청/응답, 점대점 패턴을 지원함

### 레디스 pub/sub 주요 특징

- 메모리를 사용하므로 지연 시간이 짧고 래빗MQ 대비 처리량이 높음
- 구독자가 없으면 메시지가 유실됨
- 기본적으로 영구 메시지를 지원하지 않음
- 모델이 단순해 사용하기 쉬움

### 메시지 생성 측 고려 사항

- 메시지를 생성할 때 고려할 점은 메시지 유실에 대한 것
- 오류 처리르 위해 선택할 수 있는 방법 3가지
  - 무시
  - 재시도
  - 실패 로그 남기기
- 무시하면 메시지는 유실됨
  - 단순 로그 메시지는 유실되어도 괜찮
  - 로그를 조회할때 없으면 아쉬울 수 있지만 기능 동작엔 문제가 없음
- 일시적인 네트워크 불안정과 같은 오류는 재시도를 통해 해결할 수 있음
  - 재시도하는 과정에서 중복된 메시지가 전송될 수 있음
    - 실제로는 전송에 성공했는데 네트워크 오류로 전송에 실패한 것으로 인지하고 재시도할 수 있기 때문
  - 메시징 시스템이 중복 수신을 방지하는 기능을 제공하지 않으면 소비자가 중복 메시지를 알맞게 처리해야 함
  - 메시지마다 고유 식별자를 사용하면 메시지 소비자가 중복 메시지 여부를 판단하는 데 도움이 됨
- 실패 로그는 DB에 저장할 수도 있고 파일에 남길 수도 있음
  - 후처리에 필요한 데이터를 담고 있어야 함
- 메시지 생산자는 DB 트랜잭션과의 연동도 고려해야 함
  - DB 트랜잭션이 실패했는데 메시지가 발송되면 잘못된 데이터가 전달될 수 있기 때문
- 잘못된 메시지가 전송되는 문제를 방지하려면 트랜잭션이 끝난 뒤에 메시지를 전송해야 함

### 메시지 소비 측 고려 사항

- 2가지 이유로 동일 메시지를 중복해서 처리할 수 있음
  - 메시지 생산자가 같은 데이터를 가진 메시지를 메시징 시스템에 두 번 전송
  - 소비자가 메시지를 처리하는 과정에서 오류가 발생해서 메시지 재수신
- 수신자 입장에서 동일 데이터를 가진 중복 메시지를 처리하는 방법은 메시지에 고유한 ID를 부여해서 이미 처리했는지 여부를 추적하는 것
- 메시지를 처리했는지 여부는 DB 테이블에 기록하거나 메모리에 집합으로 관리하면 됨
  - 메모리로 관리할 때는 메모리 부족 에러가 발생하는 것을 막기 위해 일정 개수의 메시지ID만 유지
- 메시지를 잘 소비하고 있는지 모니터링하는 것이 중요

### 메시지 종류: 이벤트와 커맨드

- 이벤트는 어떤 일이 발생했음을 알려주는 메시지
  - '주문함'이벤트는 주문이 생성됐다는 사실을 의미
  - '배송을 완료함'이벤트는 물건이 고객에게 전달됐다는 사실을 의미
  - 상태(데이터) 변경과 관련이 있음
  - 정해진 수신자가 없고 발생한 사건에 관심이 있는 소비자가 메시지를 수신하는 방식
- 커맨드는 무언가를 요청하는 메시지
  - 메시지를 수신할 측의 기능 실행에 초점이 맞춰져 있음
  - 수신자가 정해져 있음

## 트랜잭션 아웃박스 패턴

- 메시지 데이터 자체가 유실되지 않도록 보장하는 방법은 먼저 해당 데이터를 DB에 안전하게 저장해두는 것
- 저장된 메시지를 읽어 메시징 시스템에 전송하면 됨
- 메시지 데이터를 DB에 보관하는 방식이 트랜잭션 아웃박스 패턴의 핵심
- 트랜잭션 아웃박스 패턴은 하나의 DB 트랜잭션 내에서 2가지 작업을 수행함
  - 실제 업무 로직에 필요한 DB 변경 작업을 수행
  - 메시지 데이터를 아웃박스 테이블에 추가
- DB 트랜잭션 범위에서 아웃박스 테이블에 메시지 데이터를 추가하므로 메시지 데이터가 유실되지 않음
- 트랜잭션을 롤백하면 메시지 데이터도 함께 롤백되므로 잘못된 메시지 데이터가 전송될 일도 없음
- 발송 완료를 표시하는 2가지 방법
  - 아웃박스 테이블에 발송 상태 컬럼을 두는것
    - 컬럼은 3가지 상태(발송 대기, 발송 완료, 발송 실패)
    - 발송 대기 데이터를 조회해 발송에 성공하면 발송 완료로 변경하는 식
  - 메시지 중계 서비스가 성공적으로 전송한 마지막 메시지 ID를 별도로 기록하는 방식

## CDC(Change Data Capture)

- 변경된 데이터를 추적하고 판별해서 변경된 데이터로 작업을 수행할 수 있도록 하는 소프트웨어 설계 패턴
- DBMS는 데이터가 변경되면 그 변경 내용을 통지하는 기능을 제공하는데 CDC는 이 기능을 활용해서 구현함
- 변경 데이터는 레코드 단위로 전달됨
  - 1개 레코드를 추가하고 2개를 수정한 다음 3개를 삭제한다면 6개 레코드에 대한 변경분이 CDC 처리기에 전달됨
  - insert, update, delete 인지 구분할 수 있는 플래그를 갖음

### CDC와 데이터 위치

- CDC 처리기는 변경 데이터를 어디까지 처리했는지 기록해야 함
- CDC 처리기를 재시작할 때 마지막으로 조회한 로그부터 읽어야 함
- 그러지 않으면 CDC 처리기를 재시작하는 시간 동안 발생한 변경 데이터를 놓치게 됨

### CDC가 유용할 때

- 시스템이 복잡해서 연동 코드를 넣기 부담스러울 때 CDC를 활용
