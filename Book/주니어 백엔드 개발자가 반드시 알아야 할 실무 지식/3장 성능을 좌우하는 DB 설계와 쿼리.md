# 성능을 좌우하는 DB 설계와 쿼리

## 성능에 핵심인 DB

- DB 성능은 연동하는 모든 서버 성능에 영향을 줌
- 쿼리 실행 시간이 길어지면서 전체 서비스가 느려지는 성능 문제
- DB 자체가 문제인 상황보다 DB를 잘못 사용해서 발생하는 문제가 많음
- 서버 개발자 입장에서 조금만 신경 써도 DB 성능 문제를 충분히 줄이거나 없앨 수 있음

## 조회 트래픽을 고려한 인덱스 설계

- DB 테이블을 설계할 때는 조회 기능과 트래픽 규모를 고려해야 함
- 데이터양이 적고 동시 접속자도 적으면 테이블을 풀 스캔하더라도 성능 문제가 발생하지 않음
- 풀 스캔이 발생하지 않도록 하려면 조회 패턴을 기준으로 인덱스를 설계해야 함

### 단일 인덱스와 복합 인덱스

- 쿼리에 userId = 123, activityDate = '2024-07-31' 조건이 달려있다
- 고민할 점은 userId 단일 인덱스로 할거냐 복합 인덱스(userId, activityDate)로 할거냐
  - 사용자당 가질 수 있는 데이터가 얼마나 될지 가늠
  - 개별 사용자 기준으로 1주일에 하루 정도 방문, 평균 활동 데이터가 5건이면 1년 활동해야 260건
  - 5년해야 1500건
  - userId 컬럼만 사용하는 단일 인덱스만 해도 문제 없음
  - 회원의 활동성이 좋다면 복합 인덱스 사용을 고려해야 함

### 선택도를 고려한 인덱스 컬럼 선택

- 인덱스를 생성할 때는 선택도가 높은 컬럼을 골라야 함
- 선택도란 인덱스에서 특정 컬럼의 고유한 값 비율을 나타냄
  - 선택도가 높으면 해당 컬럼에 고유한 값이 많다는 뜻

```sql
create table member (
    memberId int not null primary key,
    gender char(1),
);
```

- 위 상황에서 gender는 M, F, N의 3개 값 중 하나를 갖기에 인덱스를 사용하면 효율이 떨어짐
- 선택도가 낮아도 인덱스 컬럼으로 적합한 상황도 있음

```sql
create table jobqueue (
    jobid varchar(16) not null primary key,
    status char(1) not null,
);
```

- 작업 실행기는 status 컬럼값이 W 인 데이터를 조회하기 때문에 status 컬럼의 선택도가 낮아도 인덱스로 추가해야 함

### 커버링 인덱스 활용하기

- 커버링 인덱스는 특정 쿼리를 실행하는 데 필요한 컬럼을 모두 포함하는 인덱스를 말함

```sql
select * from activityLog
where activityDate = '2024-07-31' and activityType = 'VISIT';
```

- activityDate 컬럼과 activityType 컬럼을 사용하는 인덱스가 있다면 인덱스를 사용해서 데이터를 빠르게 선택할 수 있음
- 인덱스를 사용해서 데이터를 선택하는 과정은 빠르지만 실제 데이터 자체는 읽어와야 함

```sql
select activityDate, activityType
from activityLog
where activityDate = '2024-07-31' and activityType = 'VISIT';
```

- 위 쿼리는 실제 데이터에 접근하지 않고 인덱스에서 데이터를 가져옴

### 인덱스는 필요한 만큼만 만들기

- 효과가 적은 인덱스를 추가하면 오히려 성능이 나빠질 수 있음
- 인덱스는 조회 속도를 빠르게 해주지만 데이터 추가, 변경, 삭제 시에는 인덱스 관리에 따른 비용이 추가되기 때문
- 인덱스 자체도 데이터이기에 많아질수록 메모리와 디스크 사용량도 증가
- 새로 추가할 쿼리가 기존에 존재하는 인덱스를 사용하지 않을 때는 요구사항을 일부 변경할 수 있는지 검토

```sql
create table reservation (
    id bigint not null primary key,
    name varchar(30) not null,
    reserveDate date not null,
    state char(2) not null,
    regDt timestamp not null
);

create index idxRdate On reservation (reserveDate);
```

- 요구 사항에 name으로만 검색하면 fullscan이지만 요구 사항을 특정 날짜에 대한 name 검색으로 하면 기존 인덱스를 사용할 수 있음

## 몇 가지 조회 성능 개선 방법

### 미리 집계하기

- 목록을 표시할 때 설문에 답현한 회원 수와 좋아요를 한 회원 수를 표시한다는 요건

```sql
select s.id, s.subject,
       (select count(*) from answer a where a.surveyId = s.id) as answerCnt,
       (select count(*) from liked l where l.surveyId = s.id) as likeCnt
from survey s 
order by id desc
limit 30;
```

- 논리적으로는 정확하지만 성능에 문제가 발생할 수 있음
  - 평균 답변자 수가 10만명이고 좋아요 회원 수가 1만명이라고 가정해보면
  - 목록 조회 1번
  - 답변자 수를 세는 쿼리 30번(각 쿼리는 10만개를 샘)
  - 좋아요 수를 세는 쿼리 30번(각 쿼리는 1만개를 샘)
- count나 sum과 같은 집계 쿼리를 조회 시점에 실행하면서 발생하는 성능 문제를 제거하는 방법은 집계 데이터를 미리 계산해서 별도 컬럼에 저장하면 됨
  - survey 테이블에 답변자 수와 좋아요 수를 저장할 컬럼을 추가하고 값을 계산해서 넣는 방식으로 구현

```sql
insert into answer values(,,,);
update survey set answwerCnt = answerCnt + 1 where surveyId = ?;
```

### 페이지 기준 목록 조회 대신 ID 기준 목록 조회 방식 사용하기

- 게시글 데이터 10만개 가정
- 화면에 10개 뿌리기
- 전체 페이지 개수는 1만개

```sql
select id, subject, writer, regdt
from article
order by id desc
limit 10 offset 0;

select id, subject, writer, regdt
from article
order by id desc
limit 10 offset 99990;
```

- 99991번째 id부터 바로 조회하면 좋겠지만 DB는 어떤 id 값이 99991번째인지 알지 모르기 때문에 데이터를 직접 세야함
- 지정한 오프셋으로 이동하기 위해 데이터를 세는 시간을 줄이는 방법은 특정 ID를 기준으로 조회하는 것
- 조회후 마지막 데이터의 id 값을 받아 다시 해당 조회 쿼리에 사용

### 조회 범위를 시간 기준으로 제한하기

- 순서대로 조회하는 방식이 아닌 월별로 조회하는 방식을 사용하면 페이지 기준 목록 조회나 ID 기준 목록 조회에 비해
쿼리가 단순해지고 성능 문제도 발생하지 않음
  - 시간 데이터 인덱스 추가
- 조회 범위를 제한하는 또 다른 방법은 최신 데이터만 조회하는 것
  - 특정 도메인에서는 최신 데이터 이외엔 의미 없을 수 있음
- 최신 데이터 위주로 조회하면 DB 성능 또한 향상됨
  - DB는 성능을 높이기 위해 메모리 캐시를 사용
  - 일반적으로 최신 데이터가 더 많이 조회되기 때문에 캐시에 최신 데이터가 적재될 확률이 높음

## 알아두면 좋을 몇 가지 주의 사항

### 쿼리 타임아웃

- 동시 사용자가 증가할 때 응답 시간이 길어지면 처리량은 감소함
- 응답 지연으로 인한 재시도는 서버 부하를 더욱 가중시킴
  - 동시 접속이 증가하면서 특정 쿼리의 실행 시간이 15초 이상으로 늘어나면 사용자는 몇 초만 지나도 서비스가 느리다고 느끼고
  재시도를 하게 됨
  - 앞선 요청이 아직 처리 중인 상황에서 새로운 요청이 유입됨
- 쿼리 타임아웃은 서비스와 기능의 특성에 따라 다르게 설정해야 함
  - 블로그 글 조회는 몇초이내
  - 결제는 긴 타임아웃 필요

### 상태 변경 기능은 복제 DB에서 조회하지 않기

- primary, replica 구조를 사용할 때 변경은 primary, 조회는 replica 사용
- 모든 select 쿼리를 무조건 replica에서 사용하는 것은 아님
- 정합성 때문
- 회원 가입, 변경, 등록, 삭제와 같이 insert, update, delete 쿼리를 실행하는 기능에서
변경 대상 데이터를 조회해야 한다면 복제 DB가 아닌 쿼리를 실행한 db에서 조회해야 데이터 불일치로 인해 발생할 수 있는 오류를 방지할 수 있음

### 배치 쿼리 실행 시간 증가

- 집계 쿼리는 특성상 많은 데이터를 스캔하기에 집계 대상 칼럼이 인덱스에 포함되어 있다면 데이터를 직접 읽지 않고 인덱스만 스캔해 집계를 수행할 수 있음
  - 커버링 인덱스를 활용
- 데이터를 일정 크기로 나누어 처리하는것도 좋음
- 데이터를 나눠서 처리하면 짧은 간격으로 집계 쿼리를 실행할 수도 있음
  - 통계 테이블에 반영된 마지막 accessDatetime 시간을 구함
  - 마지막 accessDatetime, 마지막 accessDatetime + 10분 에 속하는 accessLog 데이터를 집계
  - 위에서 구한 집계 데이터를 통계 테이블에 반영

### 타입이 다른 컬럼 조인 주의

- 조인에 사용한 컬럼의 타입이 서로 다르면 인덱스를 활용하지 못할 수 있음
- 비교 대상 컬럼의 타입을 맞추면 쿼리 실행 중 발생하는 불필요한 타입 변환을 줄일 수 있음

### 테이블 변경은 신중하게

- 데이터가 많은 테이블에 새로운 컬럼을 추가하거나 기존 열거 타입 컬럼을 변경할 때는 매우 주의해야 함
- DB 테이블 변경 방식때문
  - MySQL의 경우에는 테이블을 변경할 때 새 테이블 생성, 원본 테이블 데이터 복사, 복사 완료 후 새 테이블로 대체
  - UPDATE, INSERT, DELETE 같은 DML 작업을 허용하지 않기 때문에 복사 시간만큼 서비스가 멈춤

### DB 최대 연결 개수

- 가정
  - API 서버 세 대
  - 트래픽이 증가하고 있어 수평 확장 필요
  - DB 서버의 CPU 사용률은 20% 수준으로 여유가 있음
- API 서버의 커넥션 풀 개수가 30개일때 DB 최대 연결 개수가 100개로 설정되어 있다면 20개의 커넥션을 얻지 못하고 연결 실패가 발생함
- DB 서버 CPU 사용률이 70% 이상으로 높다면 연결 개수를 늘리면 안됨

- 비정상 상황에서의 트랜잭션 처리르 반드시 고민해야 함
- 외부 API 연동과 DB 작업이 섞이면 트랜잭션 처리가 복잡해짐
- 외부 연동은 상황에 따라 대응 방법이 달라짐
