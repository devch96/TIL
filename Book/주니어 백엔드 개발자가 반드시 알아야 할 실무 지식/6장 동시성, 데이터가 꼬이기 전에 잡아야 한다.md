# 동시성, 데이터가 꼬이기 전에 잡아야 한다

## 서버와 동시 실행

- 동시에 여러 클라이언트가 요청을 보내기 때문에 서버는 각 요청을 동시에 처리해야 함
- 동시에 처리하지 못하고 각 요청을 순차적으로 처리한다면 서버의 전체적인 성능 즉 처리량과 응답 시간이 나빠짐
- 서버가 동시에 여러 클라이언트의 요청을 처리하는 방식
  - 클라이언트 요청마다 스레드를 할당해서 처리
  - 비동기 IO(또는 논블로킹IO) 를 사용해서 처리
- 동시 실행을 고려하지 않고 코드를 만들면 찾기 어려운 버그가 발생할 수 있음
- 동시성 문제는 항상 바로 드러나지 않고 숨어 있다가 예상치 못한 순간에 나타남
- 동시성 문제는 미묘해서 재현이 잘 되지 않는 경우도 많음
  - 처음부터 동시성 문제를 염두에 두고 개발하는 것이 중요

## 프로세스 수준에서의 동시 접근 제어

### 잠금(lock)을 이용한 접근 제어

- 프로세스 수준에서 데이터를 동시에 수정하는 것을 막기 위한 일반적인 방법
- 잠금을 사용하면 공유 자원에 접근하는 스레드를 한 번에 하나로 제한할 수 있음
- 잠금은 한 번에 한 스레드만 획득할 수 있으며 여러 스레드가 동시에 잠금 획득을 시도하면 그중 하나만 획득하고 나머지는 잠금이
해제될 때까지 대기함

```java
public class UserSessions {
    private Lock lock = new ReentrantLock();
    private Map<String, UserSession> sessions = new HashMap<>();
    
    public void addUserSession(UserSession session) {
        lock.lock(); // 잠금 획득할 때까지 대기
        try {
            sessions.put(session.getSessionId(), session); // 공유 자원(Map) 접근
        } finally {
            lock.unlock(); // 잠금 해제
        }
    }
    
    public UserSession getUserSession(String sessionId) {
        lock.lock();
        try {
            return sessions.get(sessionId);
        } finally {
            lock.unlock();
        }
    }
}
```

- HashMap은 다중 스레드에서 안전하지 않음
- 여러 스레드가 HashMap의 put() 메서드를 호출하면 데이터가 유실되거나 값이 잘못 저장되는 문제가 발생할 수 있음
- 자바에는 synchronized 키워드가 존재
- synchronized 키워드를 사용하면 코드 블록이 끝나면 자동으로 잠금을 풀어주기 때문에 unlock()을 사용할 필요가 없음
- ReentrantLock은 synchronized에 없는 기능을 제공
  - 잠금 획득 대기 시간을 지정하는 기능 등
  - 자바 21버전에 추가된 가상 스레드는 synchronized 지원 안하고 ReetrantLock만 지원
    - 24부터는 synchronized 지원

### 동시 접근 제어를 위한 구성 요소

- 한 번에 한 스레드만 공유 자원에 접근할 수 있음
- 나머지 스레드는 잠금이 해제될 때까지 대기해야 함
- 잠금 외에도 동시 접근을 제어하기 위한 구성 요소로 세마포어와 읽기 쓰기 잠금이 있음

#### 세마포어

- 세마포어(Semaphore)는 동시에 실행할 수 있는 스레드 수를 제한함
- 자원에 대한 접근을 일정 수준으로 제한하고 싶을 때 사용할 수 있음
  - 외부 서비스에 대한 동시 요청을 최대 5개로 제한하고 싶을 때
- 자바 세마포어 구현체는 퍼밋(permit)
- 세마포어 사용 순서
  - 세마포어에서 퍼밋 획득(허용 가능 숫자 1 감소)
  - 코드 실행
  - 세마포어에 퍼밋 반환(허용 가능 숫자 1 증가)
- 각 스레드는 세마포어에서 퍼밋을 획득한 뒤에 코드를 실행할 수 있음

```java
public class MyClient {
    private Semaphore semaphore = new Semaphore(5);
    
    public String getData() {
        try {
            semaphore.acquire(); // 퍼밋 획득 시도
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        } 
        try {
            String data;
            return data; // 외부 연동
        } finally {
            semaphore.release(); // 퍼밋 반환
        }
    }
}
```

#### 읽기 쓰기 잠금

- 잠금을 사용하면 데이터를 변경하지 않더라도 동시에 읽기가 안됨
- 한 번에 1개 스레드만 읽기 기능을 실행할 수 있기 때문
  - 쓰기 빈도 대비 읽기 빈도가 높을 때에는 읽기 성능이 떨어지는 문제가 발생할 수 있음
- 읽기 쓰기 잠금의 특징
  - 쓰기 잠금은 한 번에 한 스레드만 구할 수 있음
  - 읽기 잠금은 한 번에 여러 스레드가 구할 수 있음
  - 한 스레드가 쓰기 잠금을 획득했다면 쓰기 잠금이 해제될 때까지 읽기 잠금을 획득할 수 없음
  - 읽기 잠금을 획득한 모든 스레드가 읽기 잠금을 해제할 때까지 쓰기 잠금을 구할 수 없음

```java
public class UserSessionRW {
    private ReadWriteLock lock = new ReetrantReadWriteLock();
    private Lock writeLock = lock.writeLock();
    private Lock readLock = lock.readLock();
    private Map<String, UserSEssion> sessions = new HashMap<>();
    
    public void addUserSession(UserSession session) {
        writeLock.lock();
        try{
            sessions.put(session.getSessionId(), session);
        } finally {
            writeLock.unlock();
        }
    }
    
    public UserSession getUserSession(String sessionId) {
        readLock.lock();
        try{
            return sessions.get(sessionId);
        } finally {
            readLock.unlock();
        }
    }
}
```

### 원자적 타입(Atomic Type)

- 잠금을 사용하면 카운터 증가에 대한 동시성 문제를 간단하게 해결할 수 있음
- 하지만 CPU 효율이 떨어지는 단점이 있음
  - 여러 스레드가 동시에 실행할 때 잠금을 확보한 스레드를 제외한 나머지 스레드는 대기하기 때문
- 잠금을 사용하지 않으면서 동시성 문제없이 카운터를 구현하는 다른 방법이 존재하는데, 그 방법은 바로 원자적 타입을 사용하는 것
  - AtomicInteger
  - AtomicLong
  - AtomicBoolean

```java
public class Increase {
    private AtomicInteger count = new AtomicInteger(0);
    
    public void inc() {
        count.incrementAndGet();
    }
    
    public int getCount() {
        return count.get();
    }
}
```

- AtomicInteger는 내부적으로 CAS 연산을 사용함
  - Compare And Swap
  - 비교 후에 교체하는 연산
- 동시에 여러 스레드가 int, long, boolean 타입의 공유 데이터를 변경한다면 잠금 대신 원자적 타입을 사용해서 동시 접근 문제를
간단하게 처리할 수 있음

### 동시성 지원 컬렉션

- 데이터를 변경하는 모든 연산에 잠금을 적용해서 한 번에 한 스레드만 접근할 수 있도록 제한함

```java
Map<String, String> map = new HashMap<>();
Map<String, String> syncMap = Collections.synchronizedMap(map);
syncMap.put("keay1", "value1"); // put 메서드는 내부적으로 synchronized로 처리됨
```

- 동시성 자체를 지원하는 컬렉션 타입을 사용해도 됨

```java
ConcurrentHashMap<String, String> map = new ConcurrentHashMap<>();
map.put("key1", "value1"); // 동시성 지원 컬렉션은 잠금 범위를 최소화함
```

## DB와 동시성

- 대부분의 DB는 명시적인 잠금 기법을 제공함
  - 선점 잠금 또는 비관적 잠금
- 선점 잠금을 사용하면 동일한 레코드에 대해 한 번에 하나의 트랜잭션만 접근할 수 있도록 제어할 수 있음
- 값을 비교해서 수정하는 방식도 있음
  - 비선점 잠금 또는 낙관적 잠금

### 선점(비관적) 잠금

- 데이터에 먼저 접근한 트랜잭션이 잠금을 획득하는 방식

```sql
select * from table for update
```

- 레코드에 대한 잠금은 트랜잭션이 종료(커밋 or 롤백)될 때 반환됨

### 비선점(낙관적) 잠금

- 명시적으로 잠금을 사용하지 않음
- 데이터를 조회한 시점의 값과 수정하려는 시점의 값이 같은지 비교하는 방식으로 동시성 문제를 처리함
- 비선점 잠금을 구현할 때는 정수 타입의 버전 컬럼을 사용함

```sql
select - , version from 테이블 where id = 아이디

update 테이블 set - , version = version + 1
where id = 아이디 and version = 위에서 조회한 version 값
```

- update 결과로 변경된 행 갯수가 0이면 이미 다른 트랜잭션이 version 값을 증가시킨 것이므로 데이터 변경에 실패한 것
  - 트랜잭션을 롤백함
- 비선점 잠금은 낙관적인 방식이기 때문에 일단 데이터 변경을 시도하고 확인하는 방식

### 외부 연동과 잠금

- 트랜잭션 범위 내에서 외부 시스템과 연동해야 한다면 비선점 잠금(낙관적) 보다는 선점 잠금(비관적)을 고려하는 것이 좋음
- 비선점 잠금을 사용하고 싶다면 트랜잭션 아웃박스 패턴을 적용해서 외부 연동을 처리하는 방식도 있음

### 증분 쿼리

- 값을 증가시키는 쿼리에서 선점 잠금을 사용한다면 잠금 대기시간 만큼 응답 시간이 길어지고 비선점 잠금을 사용하면 대기 시간은 없지만
변경 실패 에러가 자주 발생할 수 있음
- 증분 쿼리를 사용하면 됨
- DB는 joinCount = joinCount + 1을 원자적 연산으로 처리함
  - 동일 데이터에 대한 원자적 연산이 동시에 실행될 경우 순차적으로 실행함
- DB에 따라 원자적 연산이 아닐 수 있기에 원자적으로 처리되는지 반드시 검증해야 함

```sql
update SUBJECT set joinCount = joinCount + 1 where id = ?
```

## 잠금 사용 시 주의 사항

### 잠금 해제하기

- 잠금을 획득한 뒤에는 반드시 잠금을 해제해야 함
  - 잠금을 시도하는 스레드가 무한정 대기할 수 있기 때문
- 세마포어도 마찬가지
- try-finally 형태의 코드 구조를 사용

### 대기 시간 지정하기

- 잠금 획득을 시도하는 코드는 잠금을 구할 수 있을 때까지 계속 대기하는데 동시 접근이 많아지면 대기 시간이 길어지는 문제가 발생할 수 있음
- 대기 시간을 지정해야 함

```java
boolean acquired = lock.tryLock(5, TimeUnit.SECONDS);
```

### 교착 상태(deadlock) 피하기

- 한 작업에서 2개 이상의 자원의 잠금을 획득하는 코드 구조는 교착 상태에 빠지기 쉬운 전형적인 패턴
- 교착 상태는 2개 이상의 스레드가 서로가 획득한 잠금을 대기
- 교착 상태가 발생하지 않도록 신경 써야 하지만 복잡한 코드 구조에서 잠금을 사용하면 개발자 자신도 모르게 교착 상태 상황이 발생할 수 있음
  - 잠금 대기 시간을 제한해야 함

## 단일 스레드로 처리하기

- 동시성 문제가 발생하는 주된 이유는 여러 스레드가 동시에 동일 자원에 접근하기 때문
- 이를 방지하기 위해 잠금과 같은 수단을 사용해야 함
- 잘못 사용하면 교착 상태 같은 상황이 발생할 수 있기 때문에 잠금을 잘 사용해야 함
- 한 스레드만 상태를 관리하는 방식으로 구현하면 자원에 한 스레드만 접근하므로 애초에 동시성 문제가 발생하지 않게 됨
- 상태 관리 스레드는 작업 큐에서 작업을 꺼내어 필요한 데이터를 처리함

```java
while(running) {
    Job job = jobQueue.poll(1, TimeUnit.SECONDS);
    if (job == null) {
        continue;
    }
    switch (job.getType()) {
        case INC:
            obj.modifyState();
            break;
        }
}
```

- 두 스레드가 데이터 공유가 필요하면 콜백이나 큐와 같은 수단을 사용해서 데이터 복제본을 공유함
  - 복제본 대신 불변값을 공유하기도 함
- 단일 스레드로 처리하면 동시성 문제에서 자유로울 수 있으나 구조가 복잡해지는 단점이 있음
  - 논블로킹이나 비동기 IO를 사용하는 경우에는 블로킹 연산을 최소화해야 하므로 단일 스레드 처리 방식이 적합함
