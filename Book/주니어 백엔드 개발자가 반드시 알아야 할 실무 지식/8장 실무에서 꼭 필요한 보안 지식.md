# 실무에서 꼭 필요한 보안 지식

## 중요한 보안

- 보안 사고가 발생할 가능성을 낮추려면 서버 개발자는 기본적인 보안에 신경을 써야 함
- 보안은 조직 차원에서 대응해야 할 만큼 범위가 넓지만 개발자 개인이 보안에 신경 써도 많은 취약점을 없앨 수 있음

-------

## 인증과 인가

- 인증(authentication)은 사용자가 누구인지 확인하는 과정
- 인가(authorization)는 사용자에게 자원에 접근할 수 있는 권한을 부여하는 것


### 인증과 토큰

- 아이디와 암호를 입력하는 로그인은 인증의 한 형태
    - 2단계 인증, 지문 같은 생체 정보 인증
- 사용자가 누구인지 확인하는 데 성공하면 서버는 클라이언트에 문자열로 된 토큰을 제공
- 클라이언트는 각 요청마다 토큰을 전달하여 자신을 증명
- 서버는 사용자 인증이 필요한 기능에 대해 매번 아이디와 암호를 입력받지 않고 토큰을 사용해서 사용자를 식별
- 토큰을 이용해서 사용자를 식별하려면 토큰과 사용자 간의 매핑 정보를 저장해야 함
    - 서버의 별도 저장소
    - 토큰

#### 별도 저장소에 토큰과 사용자 식별자 정보 저장하기

- 서버는 토큰과 사용자 식별 정보를 DB나 레디스와 같은 별도 저장소에 보관할 수 있음
- 토큰 문자열을 생성할 때는 고유한 값을 생성해 토큰 중복으로 인해 사용자 정보가 잘못 매칭되지 않도록 해야 함
- 외부 저장소에 보관되는 정보
    - 토큰
    - 사용자 식별자
    - 생성 시간
    - 최근 사용 시간
    - 유효 시간, 클라이언트 버전 등 추가 데이터
```java
String token = ...
Optional<TokenData> tokenDataOpt = tokenStore.getTokenData(token);
TokenData tokenData = tokenDataOpt.orElseThrow(() -> new InvalidTokenException());
```
- 외부 저장소가 아닌 서버 메모리에 토큰 데이터를 저장할 수도 있음
    - 서블릿 세션이 이에 해당
    - 톰캣과 같은 서블릿 컨테이너는 메모리에 세션 객체를 저장

```java
HttpSession session = request.getSession(false);
if (session == null) {
        throw new AuthenticationException();
}
UserSessionData data = (UserSessionData) session.getAttribute("userSessionData");
if (data == null) {
        throw new AuthenticationException();
}
```

- 메모리에 토큰 데이터를 저장하는 방식을 사용할 때는 고정 세션(sticky session)이 필요함
    - 서버마다 서로 다른 토큰 집합을 저장하고 있기 때문
- 토큰 데이터를 메모리에 저장하는 방식에는 단점이 있음
    - 서버를 재시작하면 토큰 데이터가 사라짐
    - 생성할 수 있는 세션 개수가 메모리 크기에 제한을 받음

#### 토큰 자체에 사용자 식별자 정보 저장하기

- JWT
- 사용자가 로그인에 성공하면 사용자 식별자를 값으로 갖는 JWT를 생성해서 클라이언트에 토큰으로 응답

```java
String token = Jwts.builder()
        .subject("userId")
        .signWith(key)
        .compact();

return LoginResponse.of(token);

try {
Jwt<Claims> jwt = Jwts.parser().verifyWith(key).build().parseSignedClaims(jws);
String userId = jwt.getPayload().getSubject();
} catch (JwtException e) {
        throw new AuthenticationException(e);
}
```

- 토큰만 있다면 사용자가 누구인지 확인할 수 있다는 장점
    - 토큰 데이터를 저장할 필요가 없으므로 서버 구조가 간단함
    - 메모리에 토큰 데이터를 저장하지 않기 때문에 수평 확장에 용이함
- 네트워크 트래픽이 증가한다는 단점이 있음
    - 토큰 안에 데이터가 추가되므로 클라이언트 서버 간 주고받는 데이터의 크기가 증가함
    - 트래픽 규모가 크면 데이터 양 증가를 무시 못함
- 토큰 데이터를 서버에서 제어할 수 없다는 것도 단점
    - 서버에 토큰 데이터가 저장되면 쉽게 토큰 데이터를 삭제할 수 있음

#### 토큰 송수신

- 클라이언트는 서버에 토큰을 전송할 때 2가지 방식 중 하나를 사용함
    - 쿠키
    - 헤더
- 웹 사이트는 주로 쿠키 방식을 사용
    - 서버 세션(톰캣)도 쿠키를 사용해서 세션ID를 주고받음
    - 웹 브라우저는 서버가 전송한 쿠키를 모든 요청에 함께 전송하므로 토큰을 서버에 전송하기 위해 별도의 자바스크립트 코드를
      작성할 필요가 없음

#### 토큰 보안

- 토큰 자체의 보안에도 신경 써야 함
    - 서버 보안이 철저해도 클라이언트 보안이 취약하면 토큰 탈취가 일어날 수 있음
- 토큰 탈취에 대응하는 방법은 토큰 유효 시간에 제한을 두는 것
- 토큰 유효 시간에는 2가지 방식이 존재
    - 토큰 생성 시점을 기준으로 제한 시간을 두는 방식
    - 마지막 접근 시간을 기준으로 토큰 유효 시간을 정하는 것
        - 서블릿 세션이 이 방식
- 유효 시간과 함께 클라이언트 IP를 비교하면 토큰 보안이 향상됨
    - 토큰을 생성할 때 접근한 클라이언트 IP와 실제 토큰을 전송한 클라이언트 IP가 같은지 비교

### 인가와 접근 제어 모델

- 인가는 사용자가 요청한 기능을 실행할 권한이 있는지 확인하는 역할
- 접근 제어의 기본은 접근한 사용자를 토큰이나 세션으로 식별하는 것
    - API 파라미터로 로그인한 사용자의 식별자를 받으면 안 됨

```java
@GetMapping("/myinfo")
public ResponseEntity<?> getMyInfo(@RequestHeader("token") String token) {
    String userId = getUserIdByToken(token);
    MyInfoResponse info = myInfoService.getMyInfo(userId);
    return ResponseEntity.ok(info);
}
```

- 사용자가 접근할 수 있는 기능(또는 자원)을 관리하기 위한 모델을 접근 제어 모델이라고 함
- 역할 기반 접근 제어
    - RBAC 모델(Role-Based Access Control)
- 사용자 권한 부여
- RBAC를 사용할 때는 역할의 설계와 관리에 신경 써야 함
    - 역할을 무분별하게 정의하면 중복된 기능을 가진 유사한 역할이 계속 생기기 쉬움

## 데이터 암호화

- 데이터를 암호화하는 방식에는 크게 단방향 암호화와 양방향 암호화가 있음

### 단방향 암호화

- 암호화된 데이터를 복호화할 수 없는 암호화 방식
- 해시 함수를 사용해서 데이터를 해시 값으로 변환
- 해시 함수 알고리즘에는 SHA-256, MD5, BCrypt 등이 있음
- 단방향 암호화는 로그인 비밀번호 같은 문자열을 암호화하는 데 주로 사용

#### 값의 비교

- 단방향 암호화는 해시 함수로 생성한 해시 값이 같다면 두 데이터가 같다고 간주한다
- 원본 데이터로 복호화할 수 없기 때문에 사용자가 비밀번호를 잊었을 때 기존 비밀번호를 알려주는 기능 대신 초기화 후 변경 과정을 거친다

#### Salt로 보안 강화하기

- 같은 해시 알고리즘을 사용하면 동일한 원본 데이터에 대해 항상 동일한 해시 값이 생성됨
    - 해시 값이 유출되면 원본을 유추하기 쉽게 만듬
- 해시 알고리즘은 위 취약점을 보안하기 위해 솔트를 사용
    - 솔트는 임의의 값이며 암호화할 때 솔트를 함께 사용하면 솔트 값에 따라 결과 해시 값이 달라짐
- 동일한 솔트와 동일한 알고리즘을 사용해서 표를 만들지 않는 한 원본을 추측하기 어려움
- 사용자마다 서로 다른 솔트를 사용하면 보안 강도를 더 높일 수 있음

### 양방향 암호화

- 암호화와 복호화가 모두 가능한 방식
- 대칭 키 방식과 비대칭 키 방식으로 나뉨
- 대칭 키 암호화는 암호화와 복호화할 때 동일한 키를 사용함
    - 키가 유출되면 누구나 암호화된 데이터를 복호화할 수 있기에 보안이 중요
- 비대칭 키 암호화는 암호화할 때와 복호화할 때 서로 다른 키를 사용
    - 공개 키와 개인 키를 생성함
    - 공개 키는 누구에게나 공개할 수 있는것
    - 개인 키는 소유자만 접근 가능
    - 공개 키는 데이터를 암호화할 때 사용되며 개인 키는 복호화할 때 사용함
    - 키 소유자는 공개 키와 개인 키 쌍을 생성한 뒤 데이터 송신자에게 공개 키를 제공함

#### SSH의 키 쌍을 이용한 사용자 인증 과정

1. 클라이언트는 인증에 사용할 키 쌍의 ID를 서버로 전송
2. 서버는 키 ID에 해당하는 공개 키를 authorized_keys 파일에서 찾음
3. 공개 키가 존재하면 임의의 숫자를 생성해서 공개 키로 암호화
4. 암호화한 숫자를 클라이언트에 전송
5. 클라이언트는 개인 키로 암호화된 숫자를 복호화
6. 클라이언트는 복호화한 숫자와 공유 세션 키를 결합한 값의 해시를 구함
7. 클라이언트는 해시 값을 서버에 전송
8. 서버는 클라이언트가 전송한 해시 값과 서버가 임의 숫자와 공유 세션 키로 생성한 해시 값이 같은지 비교
9. 두 값이 일치하면 클라이언트를 인증

## HAMC을 이용한 데이터 검증

- HMAC
    - Hash-based Message Authentication Code
    - 메시지의 무결성과 인증을 보장하기 위해 사용하는 암호화 기술
- HMAC은 해시 함수와 비밀 키를 이용해서 2가지를 보장함
    - 메시지 무결성
        - 메시지가 중간에 위변조되지 않았음
    - 인증
        - 메시지 발신자를 인증할 수 있음
- 메시지의 발신자와 수신자는 둘만 알고 있는 비밀 키를 공유
- 메시지 발신자는 메시지를 비밀 키로 해싱해서 생성한 MAC(메시지 인증 코드)를 원본 메시지와 함께 수신자에게 전송함
- 수신자는 수신한 메시지와 비밀 키를 이용해 MAC을 다시 생성한 뒤 발신자가 보낸 MAC과 비교
    - 두 값이 같으면 메시지가 변경되지 않았음을 보장할 수 있음
    - 두 값이 다르면 메시지는 유효하지 않은 것으로 판단
- HMAC의 장점은 단순함과 효율성에 있음
    - 발신자와 수신자가 비밀 키만 공유하면 정해진 해시 알고리즘을 이용해 MAC을 생성할 수 있음
- 비밀 키 관리가 단점
    - 외부에 유출되면 보안에 취약해짐
    - 키 교체도 까다로움

### HMAC 예제 코드

```java
public static class HMAC {
    private String secretKey;

    public HMAC(String secretKey) {
        this.secretKey = secretKey;
    }

    public String hmac(String message) {
        try {
            Mac mac = Mac.getInstance("HmacSHA256");
            SecretKeySpec secretKeySpec = new SecretKeySpec(secretKey.getBytes(), "HmacSHA256");
            mac.init(secretKeySpec);
            byte[] hash = mac.doFinal(message.getBytes("UTF-8"));
            return Base64.getEncoder().encodeToString(hash);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }
}
```

## 방화벽으로 필요한 트래픽만 허용하기

- 방화벽은 물리적인 장비로 존재하기도 하고 가상 방화벽으로 존재하기도 함
- 방화벽은 네트워크 통신을 두 방향으로 제어
  - 인바운드 트래픽
    - 외부에서 내부로 유입되는 것
  - 아웃바운드 트래픽
    - 내부에서 외부로 유출되는 것
- 기본적으로 인바운드는 필수 트래픽만 허용하고 나머지는 차단함
- 아웃바운드 역시 가능하면 필수만 허용하고 나머지는 차단
  - 아웃바운드를 모두 허용하면 서버가 해킹당했을 때 해커의 중간 경유지로 악용될 수 있기 때문

## 감사 로그(audit log) 남기기

- 감사 로그는 특정 작업, 절차, 사건 또는 장치에 영향을 주는 활동의 순서를 입증하는 보안 관련 기록
  - 사용자의 로그인/로그아웃 내역
  - 암호 초기화 등 설정 변경 내역
  - 환자 기록을 조회한 의료진 정보
  - 계약서의 수정 이력

## 시큐어 코딩

### 입력 값 검증

- 클라이언트가 전송한 값이 올바르다고 가정하지 말고 모든 값을 검증해야 함
- 검사 항목으로는 필수 여부, 길이 제한, 미허용 값 등이 있음

### 개인 정보/민감 정보 암호화

- 로그인 암호와 바이오 정보처럼 인증에 사용되는 정보뿐만 아니라 주민 번호, 운전 면허 번호 같은 고유 식별 정보도
암호화해야 함

### 에러 메시지에 시스템 정보 미노출

- 에러 메시지에 내부 IP나 DB IP와 같은 시스템 정보가 노출되지 않도록 함

### 보안 통신

- HTTPS처럼 데이터를 암호화해서 데이터 유출을 방지

### CORS(Cross Origin Resource Sharing) 설정

- 허용된 도메인만 서버 자원에 접근할 수 있도록 제한

### CSRF(Cross Site Request Forgery) 대응

- 주요 기능은 타 사이트에서 위조 공격이 들어오는 것을 방지하기 위해 CSRF 토큰, SameSite 쿠키, 캡차 등을 사용
